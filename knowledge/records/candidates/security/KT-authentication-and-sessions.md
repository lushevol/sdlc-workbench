# Authentication and sessions

## Scope

This topic connects user authentication, portal sessions, and the supplied Entra migration materials.
It describes intended behavior, source design statements, and historical proposals.
It does not establish deployed behavior or approved security policy.

## Summary

The target portal authenticates users, obtains entitlements, and issues tokens for application requests.
The RATAN team owns and reviews portal policy under ICS bank security policy.
The user set session timeout ceilings and specified Entra SSO without OneMFA fallback.
[12 November clarification](../../../../tasks/ui-test-coverage-20261022/evidence/portal-ingestion-answers-20261112.md#exact-user-input)

For all portal environments, the user selected denial when an authenticated SC user lacks any registered application entity entitlement.
This is user-stated intent, not approved policy or verified enforcement.
The [retained answer](../../../../tasks/ui-test-coverage-20261022/evidence/clarification-20261022/ui-q-002-source.json) and [scope answer](../../../../tasks/ui-test-coverage-20261022/evidence/clarification-20261022/ui-q-002-scope-source.json) preserve the selections.

## Documented knowledge

### Intended session renewal

The [active-session requirement](../requirements/REQ-active-session-renewal.md#intended-scope) defines the ideal target behavior.
Eligible mouse, keyboard, and scroll activity must support continued portal-session renewal.
Idle timeout must be at most 15 minutes.
Absolute session timeout must be at most 60 minutes from portal authentication.
The absolute limit applies during activity and renewal.
Within the absolute limit, renewal can continue across the initial refresh-token expiry while access remains valid.

During manual recovery, the expiry prompt must remain open while renewal is pending.
Successful renewal must close the prompt exactly once after completion.
A rejected renewal must preserve the prompt and permit another renewal attempt under the canonical criterion conditions.
The requirement holds the canonical measurable scenarios.

The independent [intent-to-reality gap record](../../../../tasks/portal-background-session-20261019/09-intent-reality-gaps.md) holds actual implementation and observation comparisons.
Defects, passing observations, backlog, and deployment state do not redefine this intended behavior.
Human publication review remains pending for this candidate topic and its linked requirement.

### Intended logout scope

The user described the ideal logout behavior as immediate revocation of all portal sessions for the user.
The target covers the current portal session and the user's other portal sessions.
Identity-provider sessions, including Entra sessions, are outside the revocation scope.
The candidate target requires RATAN review under the applicable ICS policy.
[12 November clarification](../../../../tasks/ui-test-coverage-20261022/evidence/portal-ingestion-answers-20261112.md#exact-user-input)

#### PORTAL-LOGOUT-AC-001

```gherkin
Feature: Immediate portal logout
  @PORTAL-LOGOUT-AC-001
  Scenario: Revoke the user's portal sessions at logout
    Given a user has 2 valid portal sessions, each with a usable refresh token
    And the user has a valid Entra session
    When the user completes logout from one portal session
    And a protected action and a renewal are attempted immediately with each prior portal session
    Then 0 of the 2 protected actions succeed with those sessions
    And 0 of the 2 renewal attempts succeed with those refresh tokens
    And the Entra session remains valid
```

### Session concepts and intended lifecycle

The documents use an access token to authenticate application requests.
An idle timeout limits inactivity.
An absolute timeout limits the interval since authentication.
A refresh token supports another authentication interval without repeating the initial SSO journey.
These are documented concepts, rather than a confirmed runtime contract.
[Session version 0, lines 1–9, 19–24, 38–65](<../../../evidence/sources/confluence/FM TPT UI Guild/Microfrontend/FMO Post Trade Portal Home/MFE Session Control and Implement Refresh Token/MFE Session Control and Implement Refresh Token Version 0/page.md#L1-L65>)

Version 0 states limits below 60 minutes for absolute timeout and below 15 minutes for idle timeout.
Its examples use a 15-minute access token and a 24-hour refresh token.
It proposes an inactivity warning, session extension, single-device login, and reused-token rejection.
Those examples do not resolve the strict-limit wording or current implementation.
[Session version 0, lines 1–9, 19–24, 38–65](<../../../evidence/sources/confluence/FM TPT UI Guild/Microfrontend/FMO Post Trade Portal Home/MFE Session Control and Implement Refresh Token/MFE Session Control and Implement Refresh Token Version 0/page.md#L1-L65>)

Version 1 proposes `exp = iat + 15 minutes` for idle timeout.
It relates absolute timeout to `auth_time` and a 60-minute `max_age` interval.
Its proposed flow obtains a refresh token before access-token expiry.
A later relogin exchanges the refresh token for another access token.
It places single-device login and token-blacklist work on a backlog.
[Session version 1, lines 102–193](<../../../evidence/sources/confluence/FM TPT UI Guild/Microfrontend/FMO Post Trade Portal Home/MFE Session Control and Implement Refresh Token/MFE Session Control and Implement Refresh Token Version 1/page.md#L102-L193>)

### Historical machine-to-machine protocol detail

The reference uses OAuth2 `client_credentials` with Basic-encoded service-account credentials against FMAA. OUD authentication success returns an access-token JWT.
Its failure example returns HTTP 401 with an Unauthorized/password-validation failure response.
The machine passes the token to its secure service. That service calls FMAA introspection with token and identifier parameters.

The reference describes FMAA validation through JWKS. Successful introspection returns user_id, active, token_type, app_id, and expires_in.
Its failure cases distinguish signature verification, token expiry, and token-owner mismatch. The examples encode active as string values.
These are historical reference contracts. No credentials, token values, source-example lifetime, or HTTP tooling option becomes current policy.
