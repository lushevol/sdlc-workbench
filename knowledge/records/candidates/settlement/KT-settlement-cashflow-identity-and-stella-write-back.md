# Cashflow identity and Stella status write-back

## Scope

This draft covers Cash Settlement identity rules, FX status write-back through RATAN, and the proposed Stella lifecycle boundary.

## Summary

The identity design defines how RATAN represents source cashflows and allocates resultant cashflow IDs.
The FX write-back design uses Stella status updates to reduce duplicate payment risk.
The acknowledgement contract and the applicability of the dated proposals remain open.

## Documented knowledge

### Identity and duplicate handling

The identity design retains Stella's 12-character ID. It pads Murex 2.11 and the MxCash/Razor entry to 12 characters. It uses an M or R prefix respectively and adds zeros before the source ID. The design gives netting and split resultants new IDs unique across RATAN services and processes. The formats use N or S followed by 11 digits. The ID generator must handle concurrent requests. [Cashflow ID design](../../../../knowledge/evidence/sources/sha256/2f5d809b7453b3284e626c71d9e9b68779e1d9eea1c826c4ed3be582a1fd170f.md#L3-L7) [Resultant identity](../../../../knowledge/evidence/sources/sha256/2f5d809b7453b3284e626c71d9e9b68779e1d9eea1c826c4ed3be582a1fd170f.md#L16-L27)

The 2026 Indonesia plan proposes `ID` as the data-center prefix, `SID` for splitting, and `NID` for netting. Its table says the length should remain 12. The plan does not state that it replaces the existing N/S-plus-11-digit formats. Capacity and applicability remain unresolved. [SID/NID plan table](../../../../knowledge/evidence/sources/sha256/e444261e3322a425fe830da406e50bb5496f895b468e4becc64d8d77924817ab.md#L22) [Capacity question](../../../../knowledge/evidence/sources/sha256/e444261e3322a425fe830da406e50bb5496f895b468e4becc64d8d77924817ab.md#L22)

The issue page records an agreement: original trade ID remains stable during booking and market events. RATAN relies on that agreement to group related cashflows. It reports Murex 2.11 Counterparty Assignment as an exception. The page gives no resolution or recovery behavior. [Counterparty Assignment](../../../../knowledge/evidence/sources/sha256/a464e754b8b12df0190ba33008090f370938e052d10b114fe6ffcc17c914fd8d.md#L3-L3)

The Uber validation description checks whether each cashflow was processed using cashflow ID and version. The Stella integration proposal lists cashflow ID, business version, and status update event for duplicate filtering. The Uber description leaves the version field unspecified. [Uber validation](../../../../knowledge/evidence/sources/sha256/da608afa9a303872a78de2a2ee327b9f724c3e8e8c6308aee7882fda7991f0a5.md#L9-L15) [Stella integration proposal](../../../../knowledge/evidence/sources/sha256/0fc2d3d755dc6e3749bb531bb8a9f8bb13e4787feb609f0d790d6b8dea3d116f.md#L7-L12)

A March 2026 Uber checklist says to filter a cashflow already processed as SCBML. It says other cashflows in the same group continue. The row is marked `Verified`, but the selected view contains no execution output. The selection records a conflicting paired release summary; effective filter scope remains unresolved. [SCBML duplicate-filter row](../../../../knowledge/evidence/sources/sha256/04d5e325bc112fefb38ed3f1793aa2da4fac3fed27c45e2f8eb32c732aec48f5.md#L18-L25)

The Swift field 20 limit is 16 characters. The identity design permits alphanumeric IDs. The identity proposal describes a BCS composition using an EQ prefix and two-character branch. Resultant ID requests use `CashflowId_Type`: Netting selects N, otherwise S. These are source-specific rules. [Swift constraint](../../../../knowledge/evidence/sources/sha256/2f5d809b7453b3284e626c71d9e9b68779e1d9eea1c826c4ed3be582a1fd170f.md#L12-L14) [ID request](../../../../knowledge/evidence/sources/sha256/2f5d809b7453b3284e626c71d9e9b68779e1d9eea1c826c4ed3be582a1fd170f.md#L25-L27)

Murex distinguishes original contract ID, creator transaction ID, payment-originating trade ID, and latest trade ID. Its adaptor maps `Trade.Parent_Trade_Id` from `TrnOrginalID`, rather than creator `TrnParentID`. Defaults set both cashflow versions to zero; withdrawal mapping sets both to one. These mappings do not define a universal cross-producer identity alias. [Murex identities](../../../../knowledge/evidence/sources/sha256/1e0baa2aee58f9ff03ee0606add92a4f1d618f09b7d1521439ad19fcce1e905c.md#L25-L28) [Adaptor mappings](../../../../knowledge/evidence/sources/sha256/1e0baa2aee58f9ff03ee0606add92a4f1d618f09b7d1521439ad19fcce1e905c.md#L100-L101) [Withdrawal versions](../../../../knowledge/evidence/sources/sha256/1e0baa2aee58f9ff03ee0606add92a4f1d618f09b7d1521439ad19fcce1e905c.md#L109)

The Uber description delegates validation upstream. Invalid cashflows are retained and filtered; their errors belong in upstream ET UI. Valid cashflows emit events. Already-processed cashflows are filtered, while remaining cashflows are batch-published. This description does not identify the version field. [Uber processing boundary](../../../../knowledge/evidence/sources/sha256/da608afa9a303872a78de2a2ee327b9f724c3e8e8c6308aee7882fda7991f0a5.md#L11-L15)

### FX status write-back

The FX requirement routes Razor cashflow status through RATAN to Stella to reduce duplicate payment risk. It calls for SUSPENDED-MATURED on the matched Stella cashflow after Razor nets, splits, settles, or releases the cashflow. It does not require write-back for netting or split resultants, or for un-net or un-split events. It prefers to suppress repeat SUSPENDED-MATURED updates. [FX objective and scope](../../../../knowledge/evidence/sources/sha256/1f9c1d8fddee5e98f9e4649613648c1cd3a1a079349a84b2e4e8b31de68ccc9d.md#L3-L19)

Razor supplies no trade version under the stated assumption. RATAN matches to the latest Stella cashflow. The design compares booking entity, counterparty, currency, amount, value date, and pay or receive direction. The requirement also names a message ID. Currency conversion and amount rounding prompted proposed matching tolerances. Confirm how the message ID and tolerances enter the match. [Requirement linkage](../../../../knowledge/evidence/sources/sha256/1f9c1d8fddee5e98f9e4649613648c1cd3a1a079349a84b2e4e8b31de68ccc9d.md#L13-L19) [Match fields](../../../../knowledge/evidence/sources/sha256/1f9c1d8fddee5e98f9e4649613648c1cd3a1a079349a84b2e4e8b31de68ccc9d.md#L79-L94) [Tolerance assumptions](../../../../knowledge/evidence/sources/sha256/1f9c1d8fddee5e98f9e4649613648c1cd3a1a079349a84b2e4e8b31de68ccc9d.md#L51-L57)

An April 2024 change row requests removing currency from FX status write-back matching. The retained FX design includes currency among its match fields. These dated statements conflict; the current matching contract remains unresolved. [April 2024 change row](../../../../knowledge/evidence/sources/sha256/d7249b14bb40641f1865bae8ce6f3973613a302cdad01194ce1ed13be3c8aa23.md#L23-L23)

For new cashflows and economic amendments, RATAN waits for the Razor cashflow. For non-economic amendments, the design carries SUSPENDED-MATURED forward when the previous Stella cashflow has that status. Its technical flow includes CCPNetted, restricts reversal status to None or Correction, and skips a Razor cashflow ID that was already processed successfully. Confirm the applicable trigger set. [Amendment and status flow](../../../../knowledge/evidence/sources/sha256/1f9c1d8fddee5e98f9e4649613648c1cd3a1a079349a84b2e4e8b31de68ccc9d.md#L63-L90)

A May 2024 bug-fix row describes withdrawal of a NETTED component while its resultant is READY with Pending Ack. It says Undo should tag the new inbound component as a reversal to avoid duplicate payment. The row requests a regression case and reports a UAT pass, with evidence referenced in a bug comment. The selected view contains no execution result. [Undo reversal-tag row](../../../../knowledge/evidence/sources/sha256/a2e6ff0419954a9479d5d07a31f80b1a074c6b1cf8ac7dde44a2fe4e46755099.md#L24-L25)

The FX design treats fees separately: Stella fee cashflows remain PROJECTED and their release or settlement does not drive this hard block. Any one SUSPENDED-MATURED cashflow among a trade's two FX cashflows hard-blocks the trade. An update or cancellation lifts the block until another matching update. [Fee and block scope](../../../../knowledge/evidence/sources/sha256/1f9c1d8fddee5e98f9e4649613648c1cd3a1a079349a84b2e4e8b31de68ccc9d.md#L32-L37)

The retained tolerance proposal compares the first two currency characters, including CNY/CNH. It also records uncertainty about other CN-prefixed currencies. Its amount wording is “within decimal for non JPY and within 100 for JPY.” Exact boundaries and intended decimal semantics require clarification. These proposals do not establish an effective matching policy. [Currency proposal](../../../../knowledge/evidence/sources/sha256/1f9c1d8fddee5e98f9e4649613648c1cd3a1a079349a84b2e4e8b31de68ccc9d.md#L53) [Amount proposal](../../../../knowledge/evidence/sources/sha256/1f9c1d8fddee5e98f9e4649613648c1cd3a1a079349a84b2e4e8b31de68ccc9d.md#L57)

### Stella lifecycle and acknowledgement

The China onboarding proposal assigns cashflow generation to Stella and lifecycle handling to post-trade processing. Stella owns business and cashflow versions in the proposal. RATAN advances its minor version for internal actions and resets it when Stella supplies a new business version. The proposal sends Released and Settled back to Stella and allows only Middle Office to amend such trades. Its amendment example requires withdrawal before replacement. [Proposed ownership and hard block](../../../../knowledge/evidence/sources/sha256/0fc2d3d755dc6e3749bb531bb8a9f8bb13e4787feb609f0d790d6b8dea3d116f.md#L3-L12) [Proposed version rules](../../../../knowledge/evidence/sources/sha256/0fc2d3d755dc6e3749bb531bb8a9f8bb13e4787feb609f0d790d6b8dea3d116f.md#L16-L20) [Amendment order](../../../../knowledge/evidence/sources/sha256/0fc2d3d755dc6e3749bb531bb8a9f8bb13e4787feb609f0d790d6b8dea3d116f.md#L63-L66)

A separate design discussion distinguishes suspension in Stella from suppression in RATAN. It describes a future policy to publish all FX cashflows as PROJECTED and calls for maker-checker control on manual straight-through processing of suspended cashflows. Confirm where these rules apply before combining them with the FX write-back design. [Suspension and suppression](../../../../knowledge/evidence/sources/sha256/eb4192cfb68c5b57854823fba7f0cb0b632a4c79d6cb78c9dcc4f00edec575d9.md#L3-L22) [Manual processing](../../../../knowledge/evidence/sources/sha256/eb4192cfb68c5b57854823fba7f0cb0b632a4c79d6cb78c9dcc4f00edec575d9.md#L38-L41)

The FX assumption says write-back has no ACK/NACK or reconciliation. The technical flow stores an internal NACK for an unmatched cashflow in phase 1. The FX interface section also says Razor must supply an ACK. The SABRE interface page describes a separate Stella ACK or NACK for booking events from RATAN. These statements name different parties or steps. The applicable acknowledgement and recovery rules require confirmation. [FX assumption](../../../../knowledge/evidence/sources/sha256/1f9c1d8fddee5e98f9e4649613648c1cd3a1a079349a84b2e4e8b31de68ccc9d.md#L49) [FX design](../../../../knowledge/evidence/sources/sha256/1f9c1d8fddee5e98f9e4649613648c1cd3a1a079349a84b2e4e8b31de68ccc9d.md#L84-L99) [SABRE booking response](../../../../knowledge/evidence/sources/sha256/06cc17867a3296f811b4005254101c74dcdd1a03aa8a3829b72ad4c9e06cfeaf.md#L9-L15)

The Stella proposal adds Payment Date for Swift scheduling and keeps Stella Value Date unchanged by post-trade processing. The document leaves atomic netting and automatic reversal as questions; it provides no rollback guarantee.
