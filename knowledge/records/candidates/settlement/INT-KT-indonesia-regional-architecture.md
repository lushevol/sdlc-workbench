# Indonesia regional architecture and access intent

## Documented knowledge

### ID-01 — Regional business scope

The Indonesia proposal places local back-office data onshore while retaining the same portal and GBS KL processing.
Indonesia users access Indonesia data. Other local-country users require approval for Indonesia access.
The documented proposal also permits group users. CES regional scope and the GDC performance benchmark remain design requirements.
The source proposes no new profiles or business functionality and expects reporting continuity.

[Selected original evidence](../../../evidence/sources/sha256/b0b5690a045abb8f1c2507ff7ac44670c532301689effa45de7aabb13de83406.md#L3-L14), [Selected original evidence](../../../evidence/sources/sha256/b0b5690a045abb8f1c2507ff7ac44670c532301689effa45de7aabb13de83406.md#L32-L50).

### ID-02 — Later isolation and provisioning choice

The later solutioning requires isolation of related data, including rules and static data.
Earlier assumptions, alternatives A/B/C, and discarded shared-data sections remain historical alternatives.
The selected provisioning diagram 3 uses the GDC Murex adaptor to convert real-time and batch input into SCBML.
Message Bridge routes Indonesia events through FM Solace. Non-Indonesia events retain their existing path.
The source also mentions GDC adaptor database persistence. Its compatibility with the isolation requirement remains unresolved.
Direct downstream access to Indonesia APIs is a preference, without recorded final approval.

### ID-03 — Fixing-flag delivery without cross-country NAS

Indonesia cannot use cross-country NAS for the fixing batch.
The proposed GDC batch processing queries the adaptor for the booking entity and publishes Indonesia events to Kafka.
Message Bridge transports those events through FM Solace into Indonesia Kafka.
Indonesia consumes those events and follows the intended fixing-revert process.
The adaptor supplies the cashflow and booking-entity FMID lookup interface.

[Selected original evidence](../../../evidence/sources/sha256/46f5f44a3d404831364e71dcf7b544ef407da1616ecc655cb64dbdc7cb0650b1.md#L10-L12), [Selected original evidence](../../../evidence/sources/sha256/46f5f44a3d404831364e71dcf7b544ef407da1616ecc655cb64dbdc7cb0650b1.md#L22-L30).

### ID-07 — Regional drawer filtering proposal

The drawer design adds `entry_name` and JSON `filter_rule` to tile and audit configuration.
The Indonesia expression checks FMID `8`; the GDC expression checks whether any FMID differs from `8`.
The example uses application `51358` and `RATAN_ENTITLEMENT_RULE`. These are source-scoped configuration descriptions.
The failure table hides drawers when EMS3 is unavailable or the filter is empty.
The same table says to show a drawer when its rule mismatches. That unresolved fail-open case prevents a complete accepted failure contract.
The proposed Redis cache lifetime is 3600 seconds. It supplies no cache execution evidence.
Historical EMS2/EMS3 responsibilities do not override later explicit CES migration intent.
