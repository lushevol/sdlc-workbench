# RATAN reference and control interface responsibilities

## Scope

Selected RATAN reference, trade-control, valuation, confirmation, and proposed TIS responsibilities.
These source descriptions define separate contracts. They establish no deployed or tested behavior.

## Summary

The selected sources describe related responsibilities and conditions.
Their original authority, effective dates, and current applicability remain unresolved.

## Documented knowledge

### INT-RC-01 — Apollo validation

The source assigns trade validation to Apollo Rule Engine, application `51527`.
RATAN calls its API and saves extracted rule responses in the exception data store.
The stated purpose is post-trade detective controls and regulatory compliance.

[Selected original evidence](../../../evidence/sources/sha256/42cde8f13f70223c5ecb16d1d2f20054c15880f6e0ffa3622deaac00c3008c6e.md#L13-L14).

### INT-RC-02 — SCI counterparty enrichment

The source routes trade-detail counterparty requests through DQSL GraphQL to SCI.
BPSI supplies an authentication token. It supplies no counterparty business data.
The documented cache refresh is daily at `03:00 SGT`.
A cache miss triggers a real-time downstream request.

[Selected original evidence](../../../evidence/sources/sha256/2b5adfa1bd17fec280f1b2e3a74586200cf4f8ecb2baa71cbf4c259311d52c7a.md#L9-L21).

### INT-RC-03 — BRDM bank codes

The source assigns the global bank-code feed to BRDM.
The described route is `BRDM → FileIT → RATAN`.

[Selected original evidence](../../../evidence/sources/sha256/cf58f4c2dfb3b18a0db48a3d76dc9433cf086cb1a52ec9c61f5eb6bf87646672.md#L13-L18).

### INT-RC-04 — CDUPS stamping and confirmation

CDUPS calls RATAN for trade SSI stamping.
For Murex trades, CDUPS sends confirmation to TDS3. RATAN synchronizes trade state from TDS3 for cashflow STP.
For BCS trades booked in EDrisque, CDUPS sends confirmation directly to RATAN. TDS3 has no such confirmation data.
For FMRP trades booked in Blade, CDUPS calls Stella. Stella updates trade status and sends trade XML through TDS3.
The source separately lists Solace confirmation into RATAN and trade information from RATAN to CDUPS.

[Selected original evidence](../../../evidence/sources/sha256/908a70ef5493fb1dfc0fdb1a33ad87b8953ab4376defbb25ce2a575603ec5d0f.md#L13-L24).

### INT-RC-05 — Falcon valuation input

The source requires bond prices and FX rates from Falcon for BTS bond PV checks in C&A.
It separates Solace trade input from TDS3 and API market-data input from Falcon.
RATAN combines both inputs for real-time PV calculation.

[Selected original evidence](../../../evidence/sources/sha256/6d4cf0fa433bbfd644b09fc5b8395c3d51b8fdbe7cadb9957804b5162b82c28b.md#L13-L25).

### INT-RC-06 — Markets UDP valuation coordination

OVV notifies RATAN through Solace when PV data is ready.
RATAN then fetches PV data through the Markets UDP API for P&L calculations and CnA exceptions.
The schedule lists three intraday feed batches and later exception batches.
Its literal SGT entries pair `15:00 SGT` with `06:00 UTC`, and `16:00 SGT` with `07:00 UTC`.
These pairs do not establish one unambiguous clock schedule.
The EOD feed is `T+1 00:00 UTC`; exception processing is `T+1 01:00 UTC`.
The EOD PV supplies the previous trade version for PV-impact calculation.
For `VALUATION_DATA_VER_HIS`, the source requires advance delay-risk notification when Friday SABRE release activity can affect readiness.

[Selected original evidence](../../../evidence/sources/sha256/d4bb2ea7fd3d5edf2edc4c6afd0ad83c64ae9c06906d1e3d54a5d40e0bcf5084.md#L9-L23).

### INT-RC-07 — RDM reference responsibilities

The source assigns global reference feeds to RDM.
Currency holidays and weekends use enterprise Solace notification or FileIT. Special holidays use enterprise Solace.
Country-S3, Murex structures and strategies, rules-engine configuration, and 15a6 registered staff use FileIT.
PCT2 portfolio refresh uses job `RAT_PCT2_REFRESH` and an API through Kong Gateway.
The closing FileIT route does not erase the table's distinct Solace and API routes.

[Selected original evidence](../../../evidence/sources/sha256/7fb3ca6627fa150f817275b77be85e19bc74df087dd7ecaf28a188858e3f5d16.md#L9-L21).

### INT-RC-08 — TDS3 trade and settlement responsibilities

TDS3 is described as SABRE's trade data lake with separate trade, fixing, and cashflow indexes.
RATAN filters TDS3 trades before forwarding eligible FX-replication trades to Razor.
Trade-blotter access includes persisted trade data and real-time API queries.
Rule-service queries retrieve rate fixings for FM COO exceptions. Manual validation fetches the latest TDS3 trade version.
Settlement cashflows originate from TDS3. RATAN caches and displays `trade_external_id` and `clearing_organization_trade_id`.
BCS FX and Equity cashflows use Parent Trade Instrument and Equity Instrument Reference fields.
TDS3 spot rates support USD amount conversion for OPS amount limits.
The source distinguishes Blade/Stella trade flow from cashflows routed through TDS3 and Solace to RATAN and Razor/FMSGW.

[Selected original evidence](../../../evidence/sources/sha256/4e009274da374a02399b7d39a1fd61898d32ea4e9b5d2a41f463909df25e010a.md#L11-L56).

### INT-RC-09 — TDSX trade control

The source describes TDSX as a unified API over TDS2 and TDS3.
RATAN retrieves Payment Schedule for the Trade Blotter and calls the TDSX REST API for trade validation.
TDSX publishes Uber messages delivered to RATAN through Solace.

[Selected original evidence](../../../evidence/sources/sha256/b6e05cdf58099a9711703f9e76f0655c24f813dd09054546918c782819cea42a.md#L9-L21).

### INT-RC-10 — MDS holiday-description enrichment

TDS3 supplies Payment Holiday Source Name. MDS is the stated golden source for Payment Holiday description.
The documented design enriches trade details from `SD_TP_SYSTEM_MAP` and `SD_CALENDAR_MAIN`.
Control-M schedules one synchronization per working day at `05:00 GMT`.
The maximum request size for `SD_TP_SYSTEM_MAP` is 3,000 rows. The request timeout is 60 seconds.
MDS owns upstream data quality and cobdate validation.
The listed green zone is Saturday `12:00` to Sunday `18:00 SGT`, equivalent to Saturday `04:00` to Sunday `10:00 GMT`.

[Selected original evidence](../../../evidence/sources/sha256/93e89e4fad0532e85f5be029d5a5ae94ff8eb4b316461d8a6517dfa5f216799b.md#L9-L33).

### INT-RC-11 — Proposed TIS payment retrieval

The source requests API retrieval of payment information previously keyed manually through OLTP.
Its TIS scope is cashflows in `Released` or `Settled`, settlement means `NOX`, no reversal event, and entity FMID `10036645`.
The source disallows SSI updates after release.
Withdrawn cashflows are unavailable to TIS/OLTP queries; the source describes Settled with Reversed/Reversal flags.
This request establishes neither approval nor a deployed API. It does not define pagination, authorization, or response schemas.

[Selected original evidence](../../../evidence/sources/sha256/b0cca0bdc20bda317e9fba35272d13c88bf9968fba169156453e9d3158f68b15.md#L13-L28).

This is a source-scoped interface requirement. It does not establish current OLA ownership or runtime connectivity.

### KR-DOI — Korea TIS and downstream operating contract

The Korea operating guide repeats TIS eligibility: Released/Settled, NOX, no reversal, and entity FMID `10036645`.
Payment and receipt endpoints query by payment date. Their displayed URL placeholders require confirmation before execution.
For SCBLKR, KRO/FCY UISUS payments use codes 5338/5339 with mandatory BR-prefixed beneficiary accounts.
The same account families use 5318/5319 for mandatory non-BR beneficiary accounts.
For non-SCBLKR, KRO UISUS uses 5323 with a mandatory non-BR beneficiary.
KRO UIBOK uses 5324 with NULL or dummy beneficiary, or 5325 with mandatory non-BR beneficiary.
Receipts use 0201 for KRO UIDD and 3013 for FCY UIDD.
HTTP outcomes are 200 success, 404 missing resource, 400 malformed parameters, 401 invalid token, and 500 service error.
The guide requires OLTP accounting for Failed, Swift_suppressed, Released, and Settled, except NOX accounts matching UIDD/UISUS.
That exclusion contract differs from the separately documented NOS-or-selected-NOX allowlist. Current precedence remains unresolved.
The operating workflow monitors yesterday/today/tomorrow accounting errors in SENT, REJECTED, or MISSING_INFO and assigns handling to OLTP.
The guide specifies SWIFT for non-KRO only and manual TIS handling for KRO payments.
FinalCancelled represents an ENISIS NACK; the workflow permits exception-blotter handling or ENISIS replay.
The temporary COMP-upload requirement remains separate from strategic confirmation options. Images and current execution remain unverified.
