# Single UI SDK

The Single UI SDK is a Java library that application backends use to integrate with [[entities/fmo-post-trade-portal]] authentication. It injects an HTTP request filter that validates JWTs generated by the Single UI authentication service and exposes user context through the `userInfo` request attribute. The 22 October 2026 architecture clarification records the component as the Single UI SDK starter and treats it as a library, not a deployed service: its repository does not establish a running service or public endpoint.

## Integration purpose

The SDK is documented as the standard client for [[concepts/single-ui-sdk-authentication]], though the architecture clarification states that universal adoption across application backends remains unconfirmed. On successful validation, it makes `userId`, `entitlements`, `oud`, and `sessionId` available on the request. This separates authentication enforcement from application business-logic permissions.

The SDK also supports [[concepts/entitlement-retrieval]]: services can query [[entities/ems2]] through `AuthorizationService.getEntitlements`, or validate and extract a separate entitlement token through `JwtTokenUtil.getEntitlementsToken`. The guides explicitly forbid using an entitlement token for authentication or login.

The architecture clarification identifies a conditional servlet filter, `AuthTokenFilter`, as the source mechanism that validates supported requests and supplies request attributes. SDK configuration conditionally registers validation. That declaration is candidate architecture knowledge: the exact downstream consumers are unavailable, so reported adoption does not prove that every application backend uses the SDK.

## Artifact and version history

- **1.0.0** — artifact `com.scb.ratan:single-ui-sdk-starter`, configuration prefix `single-ui-sdk.auth`, optional `user-login-max-duration`, request context field `userEntitlements`.
- **1.1.1** — artifact renamed to `com.scb.fmoportal:fmoportal-auth-sdk`; duration property removed; request context field renamed to `entitlements`.
- **1.1.2** — adds `max_age` validation and `oud` in request context.
- **1.1.4** — adds logout session rejection and configurable public certificates.
- **1.1.4-java8** — JDK 8, Spring Boot 2.6.6 or higher.
- **1.1.4-java17** — JDK 17, Spring Boot 3.1.2 or higher.
- **2.0.0-SNAPSHOT** — Spring Boot 4.0.6 migration note; an official `2.0.0` release remains conditional on regression testing.

The architecture clarification does not identify which artifact version or configuration each consumer uses. Its evidence limits therefore leave the applicable SDK build per application unresolved.

## Protected requests and exceptions

The documented URL algorithm checks exclusions first. With an empty inclusion list it validates all remaining paths; otherwise it validates only matching inclusion paths. Configuration therefore determines which requests receive SDK authentication checks. The guides also describe `skip-jwt-headers`, which causes the SDK to skip JWT checks for matching headers, but they do not identify a trusted replacement authentication control.

The architecture clarification likewise characterizes validation as a conditional servlet filter. It does not resolve which consumers have adopted the filter, which paths they protect, or how skipped paths are secured in an active deployment.

## SDK 3.0.0 CES migration

The user selected version `3.0.0` as the target for the [[entities/ces]] migration. Requirements: preserve the old contract where possible, assess complete compatibility, and have the SDK caller supply the FMAA token. Tests are required; failure handling remains unresolved.

The intent defines two acceptance criteria:

- `SDK-CES-INTENT-AC-001` — the returned permission map must have zero missing and zero unsupported additional role-scoped permissions while preserving subject and action meaning.
- `SDK-CES-INTENT-AC-002` — the SDK must use the caller-supplied FMAA token as its bearer credential and make zero independent FMAA token-acquisition requests.

Unmapped or unsupported CES meaning remains a compatibility gap for explicit review rather than grounds for invented role attribution or extra grants.

## Relationship to portal policy

The SDK validates tokens and retrieves entitlements; it does not enforce tile visibility or launch. Those decisions belong to [[concepts/portal-entry-and-tile-authorization]], owned (per user report) by [[entities/portal-team]]. A visible tile does not imply permission to read or modify business data, and the guides do not establish automatic subject-and-action enforcement for every API.

## Known limits and open questions

- No downstream service execution or SDK compatibility build was inspected; the applicable artifact and configuration per consumer are unresolved. The architecture clarification likewise leaves universal adoption unconfirmed and does not treat the SDK repository as a deployed service.
- The SDK guide recommends entitlement caching. The current API permission rule takes effect after the applicable Auth Server Redis entry expires, with one hour for the entitlement cache and two hours for JWT parsing. The applicable cache for each protected path and cross-instance implementation remain unverified. The separate logout ideal revokes all portal sessions immediately and excludes identity-provider sessions. - The overview announces removal of EMS2 details from authentication JWTs in DEV on 30 August 2024, but no retained proof shows current environment token shapes.
- The trusted control for excluded paths or skip headers is undocumented.
- The architecture record separates user-reported topology from source-extracted declarations and executed no live requests; SDK behavior in an active portal therefore remains unverified.
