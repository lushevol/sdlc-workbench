# Single UI SDK Authentication

## Definition

Single UI SDK authentication is the request-time mechanism by which the [[entities/single-ui-sdk]] validates portal authentication tokens inside a downstream Spring application. Successful validation exposes the authenticated user context to application code. The SDK authenticates the caller; it does not itself grant business data permissions.

## How the mechanism works

The SDK injects an HTTP request filter into a downstream Spring application. The filter validates JWTs generated by the Single UI authentication service. After successful validation, the filter exposes user information through the request attribute `userInfo`.

Downstream code reads identity and session facts from that attribute. The Java 17 guide of version 1.1.4 lists `userId`, `entitlements`, `oud`, and `sessionId` in the exposed context.

## Which requests receive a check

The documented URL algorithm decides which requests the filter validates.

1. The filter evaluates exclusions first.
2. If the inclusion list is empty, the filter validates all remaining paths.
3. If the inclusion list is not empty, the filter validates only matching inclusion paths.

Configuration therefore decides which requests receive an SDK authentication check. The examples also configure `skip-jwt-headers`. Earlier guides state that a matching header causes the SDK to skip the JWT check. The supplied instructions do not identify a trusted replacement authentication control on bypassed paths. That gap prevents a complete account of protected-request behavior.

## Version and artifact history

The package identity changed across releases. Each consumer must match its actual dependency against these statements.

| Documented version | Artifact and configuration | Notable change |
| --- | --- | --- |
| 1.0.0 | `com.scb.ratan:single-ui-sdk-starter`, prefix `single-ui-sdk.auth` | Optional `user-login-max-duration`; request context field `userEntitlements` |
| 1.1.1 | `com.scb.fmoportal:fmoportal-auth-sdk` | Duration property removed; field renamed to `entitlements` |
| 1.1.2 | Same artifact | Adds `max_age` validation; adds `oud` to request context |
| 1.1.4 | Same artifact | Adds logout session rejection and configurable public certificates |

Declared platform variants are:

- Java 8 guide: JDK 8 with Spring Boot 2.6.6 or higher, artifact `1.1.4-java8`.
- Java 17 guide: JDK 17 with Spring Boot 3.1.2 or higher, artifact `1.1.4-java17`.
- Boot 4 migration note: Spring Boot 4.0.6, artifact `2.0.0-SNAPSHOT`.

The Boot 4 note makes an official `2.0.0` release conditional on regression testing. It describes separated JWT configuration, public-key configuration, and import changes. It does not show a completed release or proven consumer compatibility.

## Boundary with entitlement retrieval

The SDK filter answers who the caller is. It does not answer what the caller may do with business data. Entitlement lookup is a separate path, described in [[concepts/entitlement-retrieval]]. Version 1.1.4 documents two retrieval paths: a direct EMS2 query through `AuthorizationService.getEntitlements`, and validation and extraction of a separate entitlement token through `JwtTokenUtil.getEntitlementsToken`. The guide forbids using an entitlement token for authentication or login.

Keeping these two token types distinct is a security requirement, not a convenience. The authentication token proves identity; the entitlement token carries grants.

## Boundary with portal access

Portal tile visibility and launch authorization are decided before application data access. Those rules are recorded in [[concepts/portal-entry-and-tile-authorization]]. A visible tile does not establish permission to read or modify the business data behind it. The tile-security proposal assigns data access and editing permissions to each tile application.

The [[entities/portal-team]] owns the user-stated portal entry rules. SDK authentication is the prerequisite control that supplies the authenticated identity those rules consume.

## Unresolved questions

- Which control authenticates requests when exclusions or skip headers bypass JWT validation?
- How do applications invalidate cached entitlements and reject logged-out sessions across instances?
- Which environments currently omit entitlements from authentication tokens?
- Which SDK artifact and configuration apply to each downstream service?

The SDK overview recommends entitlement caching and mentions NGINX stickiness for multiple endpoints. It also announces removal of EMS2 details from authentication JWTs in DEV on 30 August 2024. That announcement establishes neither the present DEV state nor any production token shape.
