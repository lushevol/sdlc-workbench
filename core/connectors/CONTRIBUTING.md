# Contributing to SC Node MCP

Thank you for contributing! Please read the guidelines below before raising a pull request.

## How to Contribute

1. Create a feature branch from `main`: `git checkout -b feat/my-change`
2. Make your changes and write or update tests
3. Run `yarn pre-pr` — this refreshes the README install URLs, updates the stats in this file, and runs all tests
4. Raise a pull request with a clear description (the PR template will guide you)

## Adding or Modifying a Tool

- Tool files live in `packages/*/src/tools/`
- Register each tool with `server.tool()` following the existing pattern
- **You must update [docs/TOOLS_REFERENCE.md](docs/TOOLS_REFERENCE.md)** to document the new or changed tool

## Adding or Modifying a Prompt

- Prompts are distributed across per-package files: `packages/*/src/prompts.js`
- Add to the appropriate package's `prompts.js` (e.g. `packages/ado/src/prompts.js` for ADO prompts)
- Unified-only prompts (context management, upload UI) stay in `packages/unified/src/prompts.js`
- **You must update [docs/PROMPTS.md](docs/PROMPTS.md)** to document the new or changed prompt

## Updating Docs

Any change to a tool or prompt that is visible to consumers **must** have a corresponding doc update. The PR checklist in `.azuredevops/pull_request_template.md` will remind you.

### Documentation Guidelines

**What to update when adding a tool:**
- [`docs/TOOLS_REFERENCE.md`](docs/TOOLS_REFERENCE.md) — add a row to the relevant section
- Add corresponding prompt in the appropriate `packages/*/src/prompts.js` and document it in [`docs/PROMPTS.md`](docs/PROMPTS.md)
- The relevant package `README.md` — update tool list and count
- [`packages/unified/README.md`](packages/unified/README.md) — update total tool count
- [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — update tool counts if category totals change

**What to update when adding a Confluence tool:**
- Also update [`packages/confluence/README.md`](packages/confluence/README.md) tool list and count

**What to update when adding a SonarQube tool:**
- Also update [`packages/sonar/README.md`](packages/sonar/README.md) tool list and count
- Also update [`docs/guide/SONARQUBE_TOOLS_GUIDE.md`](docs/guide/SONARQUBE_TOOLS_GUIDE.md)

**What to update when adding an ADO Upload App tool:**
- Also update [`packages/ado-upload-app/README.md`](packages/ado-upload-app/README.md) and [`docs/ADO_UPLOAD_APP.md`](docs/ADO_UPLOAD_APP.md)

**Guide file standards (`docs/guide/`):**
- No unchecked dev-note checkboxes in committed docs (`[ ] Tested - Passed`, `[ ] Not Tested`, etc.)
- No developer-only warning banners ("⚠️ IMPORTANT: restart the MCP server before testing")
- Replace real internal data (employee names, work item IDs, production repo names) with generic placeholders before committing

**Archive policy:**
- Historical implementation notes or migration plans go in `docs/archive/`
- Every archive file must start with `> ⚠️ **ARCHIVED** — ...` notice
- Fix broken internal links when archiving (update to correct relative paths)

**Changelog:** Do not manually edit `CHANGELOG.md` files — they are auto-generated by Lerna. Version bumps are triggered via the ADO pipeline, not run manually by contributors.

## Releasing

The `scripts/release.js` script prepares a release commit locally. It bumps package versions, regenerates docs, creates a single commit, and tags each bumped package.

```bash
npm run release                              # interactive: auto-detects work item + confirms packages
npm run release -- --work-item=12900178      # explicit work item: skips detection, still confirms packages
npm run release -- --work-item=12900178 --yes  # fully non-interactive (CI / scripted use)
```

**Work item resolution (when `--work-item` is not provided):**
1. Scans the last 3 commits for a `#<id>` reference — picks the most recent match
2. Shows the detected ID and asks `[Y/n]` — press Enter or `y` to accept, `n` to type a different ID
3. If no ID is found in recent commits, prompts interactively

**Package preview:**
Before Lerna runs, the script calls `lerna changed` to list which packages have pending changes and asks for confirmation. If no packages have changes, the script exits cleanly with no side-effects.

**Flags:**
| Flag | Behaviour |
|------|-----------|
| `--work-item=<id>` | Use this ID directly; skips detection and the work item confirmation prompt |
| `--yes` | Skip all confirmation prompts (requires `--work-item` or a detectable `#<id>` in recent commits) |

After a successful run, push with: `git push --follow-tags`

## Building

Each package must be built before publishing. The pipeline handles this automatically, but you can run it locally:

```bash
yarn build              # all packages (via lerna)
cd packages/ado && yarn build  # single package
```

Built output goes into each package's `dist/` directory (gitignored). Only `dist/` is included in the published npm artefact.

## Running Tests

```bash
yarn test               # all packages
yarn test:coverage      # with coverage report
```

Coverage threshold is 90% across lines, functions, branches, and statements (enforced by vitest.config.js in each package).

## Before Every PR

```bash
yarn pre-pr
```

This runs `update-readme` (refreshes one-click install badge URLs), `update-contributing` (updates the stats block below), and `yarn test`.
