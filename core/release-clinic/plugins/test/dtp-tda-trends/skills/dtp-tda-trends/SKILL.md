# dtp-tda-trends Skill

## Purpose

This skill produces a **consolidated TDA trend and compliance report** across multiple releases.  It is the analytical layer on top of the `dtp-tda-report` skill, which assesses individual releases.

Input: one or more `TDAFindings_<STREAM>_<release_id>.json` files in the `TDAFindings/` folder (generated by `extract_tda_findings.py`).

Output: a self-contained HTML report saved to `C:\Users\<username>\Downloads\TDATrendsReport_<date>.html`.

---

## Invocation

The user will ask something like:
- "Generate a TDA trends report"
- "Analyse our TDA findings across the last N releases"
- "What are the recurring compliance issues across streams?"
- "Give me a portfolio health report from TDA findings"

---

## Input Data Format

Each `TDAFindings_*.json` has this structure:

```json
{
  "stream": "FXO",
  "release_id": "15086272",
  "report_date": "2026-08-01",
  "chg_id": "CHG1055596",
  "branch": "release/74.2.0",
  "snow_state": "N/A",
  "rwi_state": "Released",
  "report_mode": "skill",
  "collector_version": "1.8.0",
  "generator_version": "1.10.0",
  "verdict": "CONDITIONAL PASS",
  "finding_counts": {
    "critical": 0,
    "moderate": 3,
    "minor": 5,
    "looksGood": 11
  },
  "findings": {
    "critical": [
      {
        "text": "...finding text...",
        "annotation": {
          "reviewer": "Jane Doe",
          "timestamp": "2026-09-01 16:17",
          "note": "...reviewer's explanation...",
          "resolution_status": "resolved"
        }
      },
      {"text": "...another finding, never annotated...", "annotation": null}
    ],
    "moderate": ["..."],
    "minor":    ["..."],
    "looksGood":["..."]
  },
  "findings_by_area": {
    "Sonar Coverage": {"critical": 0, "moderate": 1, "minor": 0, "looksGood": 1},
    "Genie Regression": {"critical": 0, "moderate": 1, ...},
    ...
  },
  "open_finding_counts": {
    "critical": 0,
    "moderate": 2,
    "minor": 5,
    "looksGood": 11
  },
  "open_findings_by_area": {
    "Genie Regression": {"critical": 0, "moderate": 1, "minor": 0, "looksGood": 0},
    ...
  }
}
```

**Reviewer annotations.** Each item under `findings.<severity>` may carry an `annotation`
recorded directly on the HTML report by a reviewer explaining the finding (why it
happened, whether it's a false positive, or what workaround/fix resolved it).
`annotation` is `null` when no reviewer has annotated that finding. When present,
`resolution_status` is one of:

| resolution_status | Meaning | Still open/live risk? |
|---|---|---|
| `resolved`        | Reviewer confirms the underlying issue was fixed | No |
| `false_positive`  | Reviewer confirms the finding doesn't reflect a real problem | No |
| `workaround`       | A mitigation/manual workaround addresses it, but the root cause remains | **Yes** (reduced severity, but still real risk) |
| `acknowledged`    | Reviewer has seen it but it is NOT yet fixed (e.g. "will be done") | **Yes** |
| `unresolved`      | Annotated but the note doesn't indicate resolution | **Yes** |

`open_finding_counts` and `open_findings_by_area` are pre-computed by the script —
they mirror `finding_counts` / `findings_by_area` but **exclude** findings annotated
`resolved` or `false_positive`. Use the `open_*` fields as the primary signal for
trend/compliance analysis; use the raw `finding_counts` / `findings_by_area` only for
audit-trail/transparency context (e.g. showing how many findings were reviewed away).

**Backward compatibility**: older `TDAFindings_*.json` files (generated before
annotation support was added) have plain strings in `findings.<severity>`
(no `annotation` key) and lack `open_finding_counts` / `open_findings_by_area`
entirely. Treat every finding in such a file as unannotated/open — i.e. its
`open_finding_counts` equals its `finding_counts`, and `open_findings_by_area`
equals `findings_by_area`. See "Handling Edge Cases" below.

Read all `TDAFindings_*.json` files from the `scripts/tda_audit/TDAFindings/` folder.

## ADO Work Item Linking

Every `release_id` is itself the numeric ID of the ADO Release Work Item (RWI) that the TDA report was generated for. **Anywhere a release ID appears in the output report as a table cell** (the Effective Verdict table in section 2, the Per-Release Detail table in section 8, and any other per-release reference), render it as a hyperlink directly to that RWI in ADO, not as plain text — so a reviewer can jump straight from a trend/finding to the source work item to investigate further.

Build the link as:
```
https://dev.azure.com/{ado_organization}/{ado_project}/_workitems/edit/{release_id}
```

Determine `{ado_organization}`/`{ado_project}` by reading `ADO_ORGANIZATION` / `ADO_PROJECT` from the `.env` file in `scripts/` (same convention used by `run_tda_audit.py`/`rwi_tda_presence_check.py` via `tda/config.py`). If `.env` is unavailable or the values can't be read, fall back to `sc-ado` / `FMQPR` (the values used throughout this codebase/dataset) rather than leaving the link unresolved.

Render as a plain `<a href="..." target="_blank">{release_id}</a>` (no extra styling needed beyond the default link color/underline) so the cell still reads naturally as the release ID, just clickable. Do not link release IDs that appear inline inside prose/finding-text paragraphs (e.g. a mention inside a Pain Point's narrative) — only table cells whose sole content is the release ID itself.

## Report Structure

Produce a self-contained HTML report.  Use the same CSS style conventions as the `dtp-tda-report` skill (dark blue header, coloured section bands, white card findings, summary tables).  The report must contain the following sections in order:

### 1. Header
- Title: "TDA Compliance & Trends Report"
- Sub-title: date range covered (earliest to latest `report_date` in the data)
- Release count, stream count, date generated

### 2. Report Generation Method Breakdown
Every `TDAFindings_*.json` carries a `report_mode` field stamped by the extraction tooling, identifying how its source TDA report was produced:

| `report_mode` value | Meaning |
|---|---|
| `skill` | Report was authored directly by the `dtp-tda-report` chat skill (agent-driven, following SKILL.md's current rules/template). |
| `script` | Report was generated by the standalone `gen_tda_report.py` script — a separate, independently-maintained "hybrid approach" tool that may lag behind the skill's rules/template (see `dtp-tda-report`'s own guardrail against ever invoking this script from within the skill). |
| `unknown` | The source HTML's footer text didn't match either recognised pattern (e.g. a very old or hand-edited report) — generation method could not be determined. |

Produce a summary table:

| Report Generation Method | Release Count | % of Releases | Streams |
|---|---|---|---|
| Skill (`dtp-tda-report`, agent-authored) | | | |
| Script (`gen_tda_report.py`, standalone) | | | |
| Unknown / unparseable | | | |

Follow with 1–2 sentences flagging any streams relying heavily on the script path — since `gen_tda_report.py` is not guaranteed to implement every current SKILL.md rule, trend findings drawn from those releases may under-report issues the skill would otherwise catch (see also the "Mixed report modes" note under Handling Edge Cases, and the per-release **Mode** column in the Per-Release Detail Table).

**Version Adoption by Team (Stream)**. Alongside `report_mode`, each `TDAFindings_*.json` also carries a `generator_version` field — the tooling version number stamped in the source report's own footer (`"Generated by dtp-tda-report skill v{X}"` for `skill`-mode reports, `"Generated by gen_tda_report.py v{X}"` for `script`-mode reports), extracted by the same tooling that derives `report_mode`. It is `"unknown"` when the footer text couldn't be parsed, and the field is absent entirely in `TDAFindings_*.json` files produced before this field was tracked — treat both cases the same way (see Handling Edge Cases). Separately, `collector_version` (see Input Data Format above) is the version of `AutoTDAScript.py` that collected the underlying data for that release.

To compare teams against the current baseline, read the **latest known versions** directly from the `dtp-tda-report` skill's own files at run time — do not hardcode a remembered value, since these change as that skill evolves:

| Baseline | Source |
|---|---|
| Latest collector version | `COLLECTOR_VERSION` constant near the top of `dtp-tda-report/skills/dtp-tda-report/scripts/AutoTDAScript.py` |
| Latest skill version | `metadata.version` in the YAML frontmatter of `dtp-tda-report/skills/dtp-tda-report/SKILL.md` |
| Latest script version | `SKILL_VERSION` constant near the top of `dtp-tda-report/skills/dtp-tda-report/scripts/gen_tda_report.py` |

If any of these three files can't be read (e.g. the `dtp-tda-report` plugin isn't present alongside this one), show "Unknown" for that baseline rather than failing the report.

Produce a table, one row per stream, listing every distinct version seen for that stream's releases and how it compares to the relevant baseline:

| Application (Stream) | Releases | Collector Version(s) Used | Collector Status | Generator Version(s) Used (Skill/Script) | Generator Status |
|---|---|---|---|---|---|

- **Collector Version(s) Used** — every distinct `collector_version` seen across that stream's releases, comma-separated if more than one; `"Unknown"` if absent/empty for all of that stream's releases.
- **Collector Status** — green **Up to date** if every version used equals the latest collector version; amber **Behind (vX.X.X)** naming the newest version in use if all versions used are older than latest; red **Mixed Versions** if the stream has releases spread across more than one distinct collector version (an inconsistency within the team, regardless of whether any single one is current); grey **Unknown** if the only version(s) seen are unparseable/absent.
- **Generator Version(s) Used (Skill/Script)** — every distinct `generator_version` seen, annotated with the mode it came from, e.g. `1.10.0 (skill)`, `1.6.0 (script)`; `"Unknown"` if absent/unparseable.
- **Generator Status** — same status logic as Collector Status, but each entry is compared against the baseline matching its own mode (a `skill`-mode entry compares against the latest *skill* version; a `script`-mode entry compares against the latest *script* version) — a stream using both modes is only **Up to date** if every entry is current against its own respective baseline.
- Sort rows with a **Behind**, **Mixed Versions**, or **Unknown** status first (the teams most worth following up with surface at the top); **Up to date** rows last.
- Colour-code the two status cells using the same green/amber/red/grey convention as other status indicators in this report.
- Follow with 1–2 sentences naming the specific teams furthest behind on each axis (collector vs. skill/script) — this is the actionable list for pushing teams onto the latest tooling.

### 3. Executive Summary — Compliance Overview
A coloured summary panel showing:
- **Overall compliance rate**: % of releases with verdict = PASS (no CRITICAL, no MODERATE)
- **Conditional pass rate**: % with verdict = CONDITIONAL PASS (no CRITICAL, has MODERATE)
- **Blocked rate**: % with verdict = BLOCKED (has CRITICAL)
- Colour-code: green ≥80% compliant, amber 60–79%, red <60%
- **Annotation coverage**: % of CRITICAL/MODERATE findings across all releases that carry a recorded reviewer annotation (i.e. `annotation` is not null). Low coverage means trend data is based mostly on raw/unreviewed findings.
- **Effective verdict mismatches**: compute an *effective verdict* per release from `open_finding_counts` (open CRITICAL > 0 → effectively BLOCKED; no open CRITICAL but open MODERATE > 0 → effectively CONDITIONAL PASS; else PASS) and compare it to the report's own recorded `verdict`. Call out releases where they disagree — e.g. a release recorded as PASS because every CRITICAL finding was annotated `resolved`/`false_positive` (an expected, healthy mismatch — annotations did their job), versus the rarer, worth-flagging case of a release recorded as BLOCKED/CONDITIONAL despite having annotations that should have cleared it (data-entry inconsistency worth a note). In the mismatch table, hyperlink each release ID to its RWI in ADO (see "ADO Work Item Linking" above).

### 4. Annotation & Resolution Summary
A table quantifying how reviewers have been using annotations, counted across all CRITICAL/MODERATE findings in the input:

| Resolution Status | Count | % of Annotated Findings |
|---|---|---|
| resolved | | |
| false_positive | | |
| workaround | | |
| acknowledged | | |
| unresolved | | |
| (not yet annotated) | | |

Follow with 1–2 sentences noting the overall reviewed-vs-unreviewed ratio and whether `false_positive` annotations cluster in particular areas (a signal the underlying check may need tuning — see Recommendations).

**Annotation Coverage by Application**. The input data's `stream` field is the per-application grouping key (each stream corresponds to one ADO Application WI, e.g. `BLADE_BA` → "Blade BA-50665"). Immediately below the Resolution Status table, add a second table broken down per application/stream, summing raw CRITICAL + MODERATE findings (`finding_counts.critical + finding_counts.moderate`, across all that stream's releases) and how many of those individual findings carry a non-null `annotation`:

| Application (Stream) | Total Critical/Moderate Findings | Annotated | Missing Annotation | % Annotated |
|---|---|---|---|---|

- "Total Critical/Moderate Findings" = sum of raw `finding_counts.critical` + `finding_counts.moderate` across all releases for that stream (use raw counts here, not `open_*`, since this table measures review coverage, not current risk).
- "Annotated" = count of individual findings in `findings.critical` + `findings.moderate` for that stream where `annotation` is not null.
- "Missing Annotation" = Total − Annotated.
- Sort rows by "Missing Annotation" descending so the least-reviewed applications surface first. Add a final totals row.
- Colour-code "% Annotated" red if <40%, amber 40–79%, green ≥80%.
- Follow with 1–2 sentences calling out any application with notably low annotation coverage relative to the portfolio average.

**Second-level breakdown by Area (within the same table)**. Directly beneath each application's summary row, add one indented sub-row per `findings_by_area` area that has any raw CRITICAL+MODERATE occurrence for that application (sum `findings_by_area[area].critical + findings_by_area[area].moderate` across all of that stream's releases), so a reviewer can see *which specific observations* drove the application's annotation gap without leaving the table:

| (Application row) | Total | Annotated | Missing Annotation | % Annotated |
|---|---|---|---|---|
| ↳ Area A | | | | |
| ↳ Area B | | | | |

- Area name prefixed with "↳" (or an equivalent visual indent/lighter-background styling) to distinguish it from the application summary row above it.
- Per-area "Total"/"Annotated"/"Missing Annotation"/"% Annotated" use the same definitions as the application-level row, scoped to just that area's individual findings (cross-reference each finding's area the same way Section 6 does, by matching against `findings_by_area` for that release).
- Sort sub-rows within each application by "Missing Annotation" descending (ties broken by "Total" descending), so the least-reviewed areas surface first within the group.
- Only include areas with ≥1 raw CRITICAL/MODERATE occurrence for that application — omit areas with zero.
- Do not add these area sub-rows into the final totals row at the bottom of the table (the totals row remains application-level only, so it still cross-foots against the Executive Summary's portfolio-wide annotation coverage figure).
- Follow with 1–2 sentences naming the specific area(s) with the lowest % Annotated within the worst-covered application(s) — this is the actionable detail the area breakdown is meant to surface (e.g. "Genie Regression accounts for most of BLADE_BA's annotation gap, at only 20% annotated").

### 5. Per-Stream Health Table
 A table with one row per stream, using **open** (annotation-adjusted) counts so that reviewed/resolved findings don't misrepresent current health:

| Stream | Releases | PASS | CONDITIONAL | BLOCKED | Most Common Open Issue Area |
|--------|----------|------|-------------|---------|------------------------------|

- PASS/CONDITIONAL/BLOCKED here reflect the *effective verdict* (based on `open_finding_counts`), not necessarily the report's raw recorded `verdict`
- "Most Common Open Issue Area" = the area with the highest total open CRITICAL+MODERATE count (`open_findings_by_area`) across that stream's releases
- Colour-code the BLOCKED count cell red if > 0, amber if CONDITIONAL > 0

### 6. Findings Frequency Analysis — Top Recurring Issues
Two tables, driven primarily by **open** occurrences (`open_findings_by_area`) since resolved/false-positive findings no longer represent live risk. Add a footnoted raw total so reviewers can see how much was filtered out:

**Table A — CRITICAL findings by area** (areas that caused blocking across releases):
| Area | Releases Affected | Open Occurrences | Raw Occurrences | Example Finding (truncated) |

**Table B — MODERATE findings by area** (areas most commonly causing conditional passes):
| Area | Releases Affected | Open Occurrences | Raw Occurrences | Example Finding (truncated) |

Sort both tables by "Open Occurrences" descending (fall back to Raw Occurrences for ties). Only include areas with ≥1 raw occurrence. Pick the example finding's `text` field (not the annotation) for the example column; prefer an example that is still open where one exists.

### 7. Pain Points — Attention Required
A highlighted section listing areas that appear in **3 or more releases** with **open** CRITICAL or MODERATE findings (i.e. counted from `open_findings_by_area`, not raw). For each:
- Area name
- Number of releases affected (open occurrences)
- Which streams are affected
- A plain-English description of why this is a pain point and what typically needs to be done

Use judgment when reading the finding `text` to describe the root cause concisely.

Separately, call out any area where **raw** occurrences are notably higher than **open** occurrences because reviewers repeatedly marked it `false_positive` (e.g. raw 6, open 1). Flag these as **possible check-tuning candidates** rather than genuine process pain points — the automated collector may be too aggressive or mis-detecting this condition. List the area, the false-positive count, and a representative reviewer note.

### 8. Positive Trends — Areas of Consistent Strength
Areas where the majority of releases (≥70%) have a LOOKS GOOD finding and zero open CRITICAL/MODERATE in that area. Present as a brief positive summary. Where relevant, note that some of this strength reflects active reviewer remediation (findings resolved via annotation) rather than the area never having issues — this still reflects healthy risk management and is worth acknowledging.

### 9. Per-Release Detail Table
A collapsible table (closed by default) listing every release:

| Stream | Release ID | Date | Mode | Verdict | Effective Verdict | C | M | m | G | Open C | Open M | CHG | Branch |

- C/M/m/G = raw CRITICAL / MODERATE / minor / LOOKS GOOD counts (`finding_counts`); Open C/Open M = `open_finding_counts` critical/moderate
- **Mode** = that release's `report_mode` (`skill` / `script` / `unknown`), rendered as a small badge — same classification as the Report Generation Method Breakdown table in section 2 — so a reviewer can see at a glance whether any individual release's findings came from the script path
- Colour-code the Verdict and Effective Verdict cells; highlight rows where they differ
- Hyperlink the Release ID cell to its RWI in ADO (see "ADO Work Item Linking" above) so reviewers can jump straight from a trend row to the source work item

### 10. Recommendations
Based on the analysis, provide 3–6 concise, actionable recommendations for the team.  Each recommendation should:
- Name the specific area or control
- Quantify the problem using **open** occurrences (e.g. "affected 4 of 7 releases, still open")
- Suggest a concrete remediation step

Also include a recommendation for any check-tuning candidates identified in the Pain Points section (areas frequently annotated `false_positive`) — recommend the collector/rule be reviewed or its threshold adjusted so reviewers stop having to manually dismiss it.

### 11. Footer
"Generated by dtp-tda-trends skill v1.5.0 | {release_count} releases across {stream_count} streams | {date}"

## Handling Edge Cases

- **ADO org/project unresolvable**: if `.env` is missing/unreadable and the `sc-ado`/`FMQPR` fallback is used, don't fail or omit the links — just use the fallback silently (it is correct for this codebase's data today).
- **Only 1 release in input**: still produce the report but note in the executive summary that trends are not meaningful with a single data point; skip the "3+ releases" pain points section.
- **Missing fields in a JSON** (e.g. empty `report_date`): use "Unknown" as the display value; do not fail.
- **Mixed report modes** (some skill-generated, some script-generated): note in the header that script-generated reports may be missing qualitative findings (AC quality, comment context) and that the trend data reflects only deterministic checks for those releases. This is also where the Report Generation Method Breakdown table (section 2) and the per-release **Mode** column (section 9) get their data — every release must be classified, never silently omitted from that breakdown.
- **Legacy findings without annotation support** (plain strings in `findings.<severity>`, no `open_finding_counts`/`open_findings_by_area` keys): treat every finding as unannotated/open — set that release's open counts equal to its raw `finding_counts`/`findings_by_area` for the purposes of sections 2–9, and don't count it toward the Annotation & Resolution Summary's "annotated" totals.
- **Mixed annotation-era data** (some JSON files have annotation support, others don't, in the same input set): this is expected and fine — just apply the legacy fallback above per-file; don't skip or warn about the older files.
- **`generator_version` or `collector_version` missing/unparseable** (older `TDAFindings_*.json` predating version tracking, or the source report's footer couldn't be parsed): display "Unknown" in the Version Adoption by Team table rather than failing the report; don't count these rows toward either "Up to date" or "Behind" — use the dedicated grey "Unknown" status instead.
- **`dtp-tda-report` plugin files unreadable** (baseline version lookup for `COLLECTOR_VERSION` / `metadata.version` / `SKILL_VERSION` fails): show "Unknown" for the affected baseline column(s) in the Version Adoption by Team table rather than failing the whole report.
- **No TDAFindings_*.json files found**: inform the user to run `extract_tda_findings.py` first and provide the commands:
  ```
  python tda_audit/download_tda_attachments.py
  python tda_audit/extract_tda_findings.py
  ```
