# Automated repository analysis

## Execution and ownership

`scripts/graph-build.sh` -> `scripts/ratan.py graph build` -> `generate_all_graphs.py` builds a temporary bundle, validates it, and publishes it with rollback. No LLM is involved. `build_graph.py` owns canonical nodes/edges; extraction modules return declarations; `resolve_repository_relationships.py` joins identities; `repository_reports.py` produces projections. `repository_inventory.py` accounts for all direct children and manifest entries, including worktrees and source snapshots.

The census content hash covers recognized source/config suffixes under the repository, excluding dependencies, generated/build output, hidden directories, and tests. It is a reproducibility aid, not the Git commit hash or a claim of full semantic coverage. Inventory failures stop generation instead of publishing success. Unsupported repositories remain in coverage/diagnostics; they are not fabricated as Spring or web applications.

## Resolution rules

| Boundary | Evidence required | Unresolved cases |
| --- | --- | --- |
| SystemJS | Literal imported module and exact declared package identity | Missing or duplicate provider |
| Feign service | Parsed name/value and unique declared service identity | URL override, unresolved constant/property, duplicate alias |
| HTTP | Explicit EXPOSES edge, compatible method/path, and known host when present; supported nginx rewrite plus Spring `open-apis` route | External authority, missing base URL, unsupported gateway syntax, ambiguous route |
| WebSocket/STOMP | SockJS/WebSocket client path, Spring `registerStompEndpoints` literal/default path, websocket-enabled nginx route, and a unique upstream service identity | Imported wrappers or computed configuration expressions, IP-only upstreams, unsupported rewrites, ambiguous routes, and live broker reachability |
| npm package | Direct dependency and an exact package name; nested manifests included | Duplicate publishers remain ambiguous; external packages remain unresolved build boundaries |
| Maven artifact | Root direct dependency and exact groupId:artifactId; local properties resolved | External artifacts remain unresolved build boundaries; remote parent models, dependency management, profiles, and transitive/version compatibility are unsupported |
| Kafka | Producer/consumer declarations plus equal concrete topic names | Cluster/environment unknown: candidate only |

Absolute URLs retain authority during matching. Path parameters may occupy complete segments; arbitrary wildcards, regex mappings and gateway prefixes are not normalized away. Client operation names alone do not prove GraphQL providers. An API node is not a provider unless explicitly exposed.

An owned `open-apis` route can declare a `GATEWAY_TRANSPORT` operation without a controller.
The operation retains `implementation_status=UNKNOWN`.
A REST join also requires caller service identity or a known authority.
An explicit GraphQL route can establish transport ownership.
It does not establish field-level handler calls.
Conflicting identities, foreign authorities, unsupported protocols, and incompatible methods prevent these joins.

Service identity configuration is static and includes profile files; it does not select an active deployment environment. npm/Maven relationships retain scope and `dependency_kind=BUILD`; graph consumers should not call these HTTP/service invocations. Source and provider evidence are both attached to resolved links. Alias collisions produce candidates and diagnostics instead of selecting the last repository encountered.

Kafka channels are repository-scoped until cluster identity can be established. The relationship report joins matching topic declarations as `KAFKA_TOPIC_CANDIDATE`, `INFERRED`, `UNRESOLVED`. These are outside the canonical edge set so impact traversal cannot mistake a name collision for a proven event flow. Configuration-only topics remain `CONFIGURES_TOPIC`; a direction is emitted only when a listener, sender, Camel getter binding, or equivalent runtime declaration supplies it.

## Published projections

- `analysis-coverage.json`: inventory statuses, source counts/hash, extractor/evidence counts, diagnostics and limitations.
- `repository-relationships.json`: source/target repository, relationship, dependency kind, assertion/resolution status, canonical edge IDs and evidence IDs; unresolved boundaries remain visible, including repository-owned file nodes.
- `analysis-report.md`: readable census and repository-pair summary. JSON retains individual declarations.

The relationship projection is validated by recomputing it from the graph. Every generated artifact is checksummed in the manifest. MCP computes relationship responses from the same loaded graph snapshot, and verifies coverage against its manifest checksum. These outputs supplement the canonical graph; they are not competing sources of runtime truth.

## Current limits and extension points

The regression-backed extraction surface is deliberately narrower than the target references:

| Extractor | Implemented forms | Diagnostics and remaining limits |
| --- | --- | --- |
| Spring provider | Direct `Controller`/`RestController` declarations; class/method path composition; arrays and declaration-local final string constants; standard request mappings; combined HTTP-method union; static `open-apis.apis` route declarations; explicit `protocol: GRAPHQL`/`transport`/`type` open-api routes; DGS `@DgsQuery`/`@DgsMutation`/`@DgsSubscription` and Spring GraphQL `@QueryMapping`/`@MutationMapping`/`@SubscriptionMapping` root fields; root and nested `@DgsData`/`@SchemaMapping` fields | Feign declarations never become providers. Unknown prefixes/constants, composed/inherited provider annotations, ambiguous mappings and unsupported GraphQL resolver annotations produce diagnostics. GraphQL schema-only fields, resolver-to-schema type checking, context paths, content negotiation and deployment activation are not inferred. An explicit GraphQL open-api route creates a transport operation only when its service alias is unique; it does not infer field-level GraphQL ownership from resolver annotations. |
| Feign client | Literal `@FeignClient` service identity plus method-level `@RequestMapping`/`@GetMapping`/`@PostMapping`/`@PutMapping`/`@DeleteMapping`/`@PatchMapping` paths and methods | URL overrides, unresolved constants/properties, composed annotations, inherited mappings and generated clients remain unresolved. Method paths are static contract evidence; they do not prove an active remote service. |
| Web invocation | Selected `fetch`, axios/request/method-shaped calls; official RTK Query base queries, inspected custom base-query wrappers, and imported API `injectEndpoints` declarations; `HttpLink`/`GraphQLClient`; WebSocket, SockJS, STOMP, and WebSocket-link endpoints; unique file-local/imported literal constants, object-member URL values, simple templates, bounded local URL helpers, `.replace` path templates, and bounded local GraphQL/WebSocket wrappers; protocol per invocation | Ordinary web invocation extraction emits `/api/` paths. RTK REST endpoints also support static absolute HTTP URLs. Feature-flagged helper branches are emitted as `INFERRED` alternatives. Unresolved explicit clients and unbound API literals produce diagnostics; imported wrappers, nonliteral/computed configuration, general receiver type checking, arbitrary generated clients, unsupported URL base composition and compiler-level scope resolution remain unsupported. RTK factory imports and wrapper URL/method forwarding require source evidence. Custom client forwarding remains inferred without known HTTP client evidence. Missing wrapper methods remain unknown, not POST by mutation naming. Method-shaped calls are syntax candidates, not type-checked HTTP clients. Supported nginx rewrites and Spring `open-apis` routes can resolve frontend REST calls; explicitly declared GraphQL open-api routes can resolve the GraphQL transport operation to a uniquely identified service; websocket-enabled nginx routes can resolve SockJS/STOMP paths to exposed Spring endpoints when the upstream service identity is declared. |
| Java URI HTTP client | `new URI(...)` or `URI.create(...)` passed to a recognised HTTP client method; literal URLs and static String fields resolved through exact owners, local scope, and imports; supporting constant evidence | Dynamic, unimported, mutable, or ambiguous URI expressions remain `UNRESOLVED_JAVA_HTTP_URI` diagnostics. The extractor records static authority/path evidence; it does not prove deployment, client typing, or runtime reachability. |
| Spring WebSocket provider | `extract_websocket_endpoints.py` resolves `registerStompEndpoints` with literal endpoint values or same-repository `endpoints` defaults | Dynamic endpoint properties, broker destinations, message handlers, and deployment activation remain unresolved |
| Kafka and Camel channels | Parsed YAML/properties values; listener topics/arrays; exact class/import constants; property/default and known configuration getter bindings; KafkaTemplate topic, ProducerRecord, and KafkaHeaders.TOPIC sends; bounded typed helper parameters and wrappers; literal or exact getter-bound Camel Kafka/file/HTTP routes | Helper analysis requires unique local implementations and supported topic forwarding. Equal-arity overloads, multiple topic parameters, reassigned/dynamic callers, computed returns, generated/external helpers, patterns, active profiles, and cluster identity remain unresolved. Constructor topic bindings require explicit assignments or declared RequiredArgsConstructor final uninitialized fields. Kafka helper parameters become diagnostics, not topic identities. Camel loop bindings retain the exact collection identity. Configuration-only values do not prove publication/consumption. File, HTTP, and unknown routes use message_channels. |
| Database | Spring Data entity references and MyBatis-Plus conventions (inferred); literal `@Table` positional/name/value mappings, including standalone entities; literal framework `.withTableName(...)`/`.tableName(...)` configuration; literal native queries/JDBC SQL; mapper XML in `src/main/resources/mapperxml`; declaration-level table access and client provenance retained through aggregation | Entity-only and framework configuration declarations are inferred READ_WRITE mappings; they identify a table boundary but do not prove a concrete CRUD call. SQL extraction uses text patterns, not a SQL/compiler model. Dynamic SQL, escaping/text blocks, imported query constants, stored procedures, overloaded client aliases and ORM method execution are outside supported proof. Migrations do not establish runtime use. These general gaps are stated here; absence of a per-call diagnostic does not establish support. |
| Redis | Parsed known `spring.redis`/`spring.data.redis` properties and actual Java type declarations or constructors from known Spring Redis imports emit a repository-scoped cache node and `CONNECTS_TO` edge | Imports, comments, strings, unrelated Redis maps, and custom type names alone do not establish a dependency. Cluster identity, key-level access, serializers, TTL behavior, and deployment reachability remain unresolved. |
| Local file access | Parsed imported or typed Java `Files`, `FileUtils`, `File`, and file-stream API calls; direction from the supported method and overload | Each repository has its own FILE boundary with `path_identity=UNKNOWN`. Arguments are omitted. Static imports, helper dataflow, generic stream types, and SFTP require separate adapters. No shared file identity or cross-repository join is inferred. |
| Internal gRPC/data-provider SDK | Explicit import and declared variable of `RatanBusinessDataProviderService` with a direct `performCashflowInternallyQuery(...)` call; exact `com.scb.ratan.grpc.sdk:ratanone-data-provider-internal-client` Maven coordinate is retained as corroborating build evidence | The external provider and channel/authority remain unresolved. Generic `@GrpcClient`, `ManagedChannel`, generated stubs, `.proto` files, wildcard/imported aliases, protobuf serialization, and tracing-only gRPC configuration are outside this extractor. An SDK dependency without a direct call does not create a runtime edge. |

`tests/test_graph_extraction.py` covers composed providers, method conditions, mixed protocols, numeric Kafka settings, unresolved topic expressions and multiple database declarations. `tests/test_graph_validation.py` checks schema rejection, provider/access contradictions, projection consistency and publication rollback. Unsupported layout/stack gaps appear in the repository census even when no extractor runs.

Runtime extraction currently targets root `src` (web) and `src/main/java`/resources (Maven). Nested `package.json` files contribute package identity and build dependency evidence, but their runtime source layouts are not extracted. Gradle, Kotlin, Python, Go and other stacks need dedicated extraction adapters. Existing frontend grouping and some platform detection still use text heuristics. AST extraction covers selected web calls, Spring mappings, Feign identities and method contracts, Kafka forms, and database declarations; it is not compiler-level call/data-flow analysis. Gateway extraction covers nginx `location`/`rewrite`/`proxy_pass` target paths and Spring `open-apis.apis` forms; websocket route joins require an `Upgrade` header, a declared upstream service identity, and an exact rewritten endpoint path.

Reflection, custom composed annotations, nonliteral cross-file constant resolution, generated clients, dynamic configurations beyond the supported route forms, active profiles, shared database identities, GraphQL schema-only fields and resolver-to-schema type checking need further adapters. Camel `from(...)` and `getEndpoint(...)` values are supported only when a Java getter binds to an exact configuration key; arbitrary dynamic expressions remain unresolved. Local/file-transfer strategies and SFTP dependencies without an instantiated SFTP client remain unsupported or build-only evidence. The detailed architecture references describe desired extraction behavior, not guaranteed implemented support. Keep these gaps explicit in coverage until regression-backed scripts implement them.

Business descriptions remain source-inferred unless enriched from authoritative knowledge. Do not infer runtime reachability or active deployment from a declaration. No cross-repository completeness score is meaningful without reporting supported protocols, layout gaps, and unresolved boundaries.

DQSL and search-engine name references remain `INFERRED` and `UNRESOLVED`.
Their diagnostics require a bound runtime client call before a confirmed dependency claim.
DTOs, interfaces, and source directory names do not prove platform queries.
Use the [dependency source audit](dependency-audit.md) after each extraction change set.
