For your workbench, I recommend that the `capability-learning`**&#x20;skill acts as a Skill Lifecycle Manager**. Its responsibility is not simply to generate `SKILL.md` files, but to discover, create, improve, validate, and maintain reusable capabilities from engineering sessions.

It should contain **six functional areas**, supported by reference documents and executable scripts.

## **1. Core responsibilities**

| Module          | Responsibility                                        | Example                                           |
| --------------- | ----------------------------------------------------- | ------------------------------------------------- |
| Discovery       | Identify reusable knowledge during engineering work   | Discover ADO artifact naming conventions          |
| Extraction      | Convert discoveries into structured knowledge         | Extract API contracts and workflow conditions     |
| Reconciliation  | Compare discoveries against existing skills           | Identify an existing ADO deployment skill         |
| Skill authoring | Create or improve skills                              | Add an artifact-resolution step                   |
| Validation      | Verify evidence, behavior, and security               | Test artifact selection against pipeline fixtures |
| Maintenance     | Track changes, contradictions, and obsolete knowledge | Update a CES migration rule when approved         |

These are logical responsibilities. They do not need to be six separate skills or services.

## **2. Recommended skill structure**

Use one `capability-learning` skill with progressively loaded instructions.

**capability-learning/**

**SKILL.md**

Main entry point: triggers, workflow, decision logic, constraints, expected outputs

**references/**

discovery-taxonomy.md, evidence-policy.md, reconciliation-rules.md, skill-authoring.md, promotion-policy.md

**assets/**

Templates for discoveries, capability manifests, evidence records, and change proposals

**examples/**

ADO workflow discovery, CES contract change, conflicting evidence, successful skill update

Keep shared executable logic outside this skill, inside your workbench's `packages/capability-engine/`. That engine should handle deterministic extraction records, metadata matching, validation, and promotion.

This separation follows the Agent Skills model, where `SKILL.md` defines the task procedure and supporting files are loaded only when needed.&#x20;

## **3. What should be inside&#x20;**`SKILL.md`**?**

Here is the proposed core content.

```
---
name: capability-learning
description: >
  Discover, extract, validate, create, and maintain
  reusable workbench capabilities from engineering
  sessions. Use when new system knowledge, API
  contracts, operational workflows, business rules,
  or verified resolutions are discovered, and when
  existing skills require improvement.
compatibility: >
  Local workbench; Node.js; Git; no MCP required.
---

# Capability Learning

## Objective

Continuously improve workbench capabilities through
evidence-backed knowledge discovered during
engineering tasks.

Prioritize the user's primary task.

## When to activate

- A previously unknown contract is discovered.
- A reusable workflow is successfully executed.
- An existing skill is found incomplete or incorrect.
- An operational failure is investigated and resolved.
- New domain rules or integration conventions emerge.
- A task checkpoint identifies reusable discoveries.
- A pending discovery requires reconciliation.

Do not create skills for isolated, non-reusable facts.

## Learning workflow

### Step 1 — Discover

Identify new or changed knowledge from the current task.

Separate observed facts from inferred conclusions.

### Step 2 — Extract

Classify information as:
- System knowledge
- Contract
- Business rule
- Workflow
- Operational experience

Produce a structured discovery record.

See references/discovery-taxonomy.md.

### Step 3 — Reconcile

Search existing capabilities.

Determine whether the discovery should:
- CREATE a capability
- EXTEND an existing capability
- CORRECT incorrect information
- REPLACE obsolete behavior
- DEPRECATE a capability
- Make NO_CHANGE

Prefer improving an existing capability.

See references/reconciliation-rules.md.

### Step 4 — Author

If a new or updated skill is required:

1. Identify its task and activation triggers.
2. Identify its scope and prerequisites.
3. Reference authoritative knowledge and contracts.
4. Reuse existing connector scripts.
5. Define an executable workflow.
6. Define verification and failure handling.
7. Add appropriate tests and examples.

See references/skill-authoring.md.

### Step 5 — Validate

Verify:
- Evidence and provenance
- Applicability scope
- Contract consistency
- Skill structure
- Dependencies
- Permission boundaries
- Script behavior
- Regression tests

Never treat unsupported assumptions as verified.

### Step 6 — Promote

Apply the configured promotion policy.

Promote safe, verified changes automatically
when permitted.

Keep high-risk or unverified changes as candidates.

Record change history and rollback information.

See references/promotion-policy.md.

## Operational rules

- Never interrupt normal engineering unnecessarily.
- Never duplicate existing capabilities.
- Never persist secrets or sensitive payloads.
- Never promote unverified business rules.
- Never expand execution permissions automatically.
- Never mutate production systems for testing.
- Use Git to maintain auditable revisions.
- Preserve unresolved discoveries as candidates.
- Keep knowledge separate from executable skills.

## Expected outputs

For each meaningful discovery, produce either:

1. A new knowledge or contract record.
2. An update to an existing capability.
3. A validated new skill.
4. A pending change requiring verification.
5. A no-change decision with justification.

All changes must reference supporting evidence.
```

This is the agent-facing procedure. It should stay relatively short. Detailed classification rules, policies, and templates belong in separate reference files.

## **4. What should generated domain skills contain?**

The learning skill should create and maintain domain skills using a consistent contract.

For example, `ado-deploy-artifact` and `ces-entitlement-migration` should follow the same structure even though they perform different tasks.

| Section           | Required contents                                         |
| ----------------- | --------------------------------------------------------- |
| Identity          | Name, description, supported task                         |
| Activation        | When the agent should use the skill                       |
| Scope             | Applicable systems, repositories, environments            |
| Preconditions     | Permissions, configuration, inputs                        |
| Knowledge         | References to verified domain knowledge                   |
| Contracts         | APIs, schemas, and interface dependencies                 |
| Execution         | Step-by-step actions using existing scripts               |
| Verification      | Expected outcomes and postconditions                      |
| Recovery          | Errors, alternative paths, retry constraints              |
| Safety            | Read/write permissions, approval requirements             |
| Learning feedback | What to capture when the workflow reveals new information |

For example, an ADO skill should describe **how to resolve the correct build artifact** and reference the underlying naming convention in the contract registry, rather than bury that convention inside long prompts.

The CES skill should describe **how to assess and verify entitlement migration** while referencing approved mapping rules and migration baselines.

Both should have a feedback mechanism so new evidence can improve them.

## **5. The learning feedback loop**

Every generated skill should include a small section that makes it compatible with the capability-learning system.

Example:

```
## Learning feedback

When executing this skill:

1. Detect previously undocumented behavior.
2. Record changes in contracts or prerequisites.
3. Capture verified failures and their resolution.
4. Identify outdated or contradictory instructions.
5. Submit reusable findings to capability-learning.
6. Do not directly modify approved business rules
   or executable behavior without validation.

```

The shared learning engine owns the feedback lifecycle. Individual skills only need to identify domain-specific signals and provide evidence.

**Execute ADO / CES skill**

**Capture new observations**

**Capability Learning**

Update knowledge

Improve skill

Flag conflict

**Validate and promote**

Improved capabilities are available to subsequent sessions

## **6. What must live outside the skill?**

There are three essential supporting mechanisms.

**Always-on agent instructions:** Add a small rule to your root `AGENTS.md` requiring the agent to consult existing capabilities before work and perform a learning checkpoint after meaningful tasks.

**Agent lifecycle hooks:** Configure supported hooks for Claude Code and Copilot to capture events reliably. A skill by itself cannot guarantee activation after every relevant session. GitHub and Anthropic distinguish skills from hooks for exactly this reason.&#x20;

**Shared capability engine:** Provide reusable Node.js scripts for storing evidence, searching capabilities, detecting conflicts, validating modifications, and applying approved updates. Avoid rewriting this logic inside every domain skill.

## **7. My recommended minimum viable version**

For V1, I would limit the implementation to these five deliverables:

1. **One&#x20;**`capability-learning/SKILL.md` defining the full learning workflow.
2. **Five reference documents** for classification, evidence, reconciliation, authoring, and promotion.
3. **One shared Node.js capability engine** implementing capture, reconciliation, validation, and updates.
4. **Agent instructions and lifecycle adapters** for automatic execution where supported.
5. **Two demonstration skills:** ADO artifact deployment and CES entitlement migration.

Do not initially build a separate memory service, knowledge graph, vector database, or capability-management UI.

The most important acceptance criterion is this:

**An agent discovers something new about ADO in Session A. In Session B, another agent retrieves that discovery, improves the existing ADO skill, and validates it. In Session C, the improved skill works without access to either previous conversation.**

That is the core behavior the `capability-learning` skill and its supporting infrastructure must deliver.
